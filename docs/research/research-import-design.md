# Research candidate import: design (#237)

Status: **proposal for maintainer approval.** Only the dry run exists
(`POST /api/admin/research/import/dry-run`, App Creator only, writes nothing).
The real import is a separate L3 issue and needs `l3-go`.

Staging is migration 045 (`catalogue_candidates`, `catalogue_evidence`). The
spreadsheet importers are never used for research candidates: they carry no
evidence or approval attribution.

## 1. Eligibility

A candidate can be imported only if all of these hold. The dry run reports the
first failing rule as the refusal reason.

| Rule | Refusal reason |
|---|---|
| `entity_type = 'pin'` (sets are not imported here) | `not_a_pin` |
| `status = 'approved'` | `not_approved` |
| `direct_verified_by` is set | `not_directly_verified` |
| `decided_by` is set | `not_attributed` |
| `duplicate_pin_id` is null and `duplicate_status` is not `DUPLICATE*` / `PROBABLE*` | `catalogue_duplicate` |
| No `review_reasons` entry mentions a duplicate | `flagged_duplicate` |
| Required fields present (below) | `missing_required_fields` |
| No live pin has the same title and collection (checked at request time) | `catalogue_duplicate` |

Migration 045 backs this with `candidate_approval_is_attributed` and
`candidate_import_creates_new_pin`. An import never overwrites a pin; enriching
an existing pin goes through audited field changes, not this path.

## 2. Field mapping (`proposed` → `pins`)

`proposed` holds Master Catalogue-shaped keys.

| `proposed` key | `pins` column | Notes |
|---|---|---|
| Pin name | `title` | **Required** |
| Brand | `brand` | **Required** |
| Release year | `release_year` | **Required**, integer |
| Main character / Characters | `main_character` / `all_characters` | At least one required |
| Series / Collection, else Categories | `collection` | |
| Release date | `release_date` | |
| Edition type | `edition_type` | |
| Edition size | `limited_edition_size` | integer |
| Park / Retailer | `retailer` | |
| Original price, Currency | `retail_price`, `currency` | |
| other keys (Release scope, Release wave, Collection type, …) | not imported | stay in staging for a later mapping decision |

Open question for the maintainer: the pilot sample has no `Pin name` for any
candidate, so today every one would be refused as `missing_required_fields`.
Either the research engine should emit it, or the real import needs an agreed
title rule. The dry run never invents a title.

## 3. Ids

`pins.id` is generated by the database. `pinhunt_id` is minted by
`next_pinhunt_id()` (migration 045, sequence-backed, no `max()+1` race) inside
the import transaction, so a failed row leaves no gap-visible half state.
The dry run returns no `pinhunt_id`.

## 4. Provenance

- Each created pin gets `import_batch_id` (a new `import_batches` row) and
  `catalogue_source = 'research_import'` (the value must be checked against
  existing constraints when the migration/L3 work is written).
- The candidate is updated in the same transaction: `status = 'imported'`,
  `imported_pin_id`, `import_batch_id`.
- Evidence rows stay attached to the candidate (`catalogue_evidence`); the pin
  is traced back through `catalogue_candidates.imported_pin_id`. Nothing is
  copied onto `pins`, so evidence stays immutable.
- `decided_by`, `direct_verified_by` and `decision_notes` remain on the candidate.

## 5. Visibility

Imported pins are inserted with `verification_status = 'needs_source_verification'`,
`is_seed_record = true`, `needs_review = true`. Public reads require
`verified`, so they are **not public**. Making them public is a separate,
explicit publish decision (out of scope here).

## 6. Batch size and atomicity

- At most **50** candidates per request (`MAX_IMPORT_BATCH`).
- All-or-nothing per batch: one transaction; any refusal found at write time
  aborts it and reports which candidate. The dry run is run first and its
  `wouldCreate` list is the only input the real import accepts.
- Staging first: run against the staging project, verify, then production.

## 7. Rollback by `import_batch_id`

1. Delete `pins` where `import_batch_id = :batch` and `catalogue_source = 'research_import'`
   (only while none of them has user data: collection entries, trades, images).
   If any has, stop and decide by hand.
2. Reset the batch's candidates to `approved`, clearing `imported_pin_id` and
   `import_batch_id` (`candidate_import_creates_new_pin` only constrains `imported`).
3. Mark the `import_batches` row rolled back.

Rollback SQL is part of the real import's L3 PR, with a human apply runbook.

## 8. Duplicate refusal

Exact or probable duplicates (`duplicate_pin_id`, `duplicate_status`), anything
flagged as a possible duplicate, and a live pin with the same title and
collection are refused with a reason. They are never merged or overwritten.
